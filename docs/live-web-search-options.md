# Live 会話中のWeb検索：現状と選択肢（未実装）

2026-10-29時点の検討。ユーザー指示により検索機能の実装・設定変更は行っていない。

## 現状

Live は会話を担当し、client delegation でカーネルの処理へ委譲する。
現在のフロントエンドの能力一覧は視覚・機体や外部への操作・身体状態と記憶で、Web検索がない。
「イコールラブって知ってる」「曲の歌詞が好き」のような会話は雑談に分類され、
`Generate <|SpawnThinking|>` による委譲が発生しない。したがって既存ChatGPTも呼ばれない。
このログから、Liveがその対象について十分な知識を持っているかどうかまでは判断できない。

GPT-Live自体が調査をできないという制限ではなく、検索はバックエンドへ接続して使う機能。
[公式の委譲仕様](https://developers.openai.com/api/docs/guides/live-delegation)では、
client delegation で任意のエージェントを使え、Responses delegation では `web_search` を含むホスト型ツールを設定できる。
検索を許可するだけでなく、Liveに「いつ調査を依頼するか」を伝える必要がある。

## 選択肢

| 案 | 動作 | 利点 | 制約 |
|---|---|---|---|
| A: 既存ChatGPTへ検索を委譲 | 実在の対象に関する調査依頼をブラウザの既存モデルへ送り、結果をLiveに戻す | 現在の構成を活用できる | DOM依存が残り、機体制御・記憶と同じキューで待つ |
| B: 検索だけ独立したAPI経路 | client delegationを維持し、検索依頼だけ検索用バックエンドで実行する | 機体・記憶のキューから分離でき、検索結果と出典を構造化しやすい | 新しいAPI処理と検索の利用コストが加わる |
| C: Responses delegationへ移行 | Liveの設定でResponsesモデルとWeb検索・機体ツールを接続する | 公式の自動委譲を使える | 現在の機体制御・監査との接続を再設計する必要がある |

今の構成を保ってまず試すならA。会話中の検索を頻繁に使い、応答待ちの独立性を重視するならBが適している。
機体制御用モデルを変更する必要はない。

## 会話としての推奨動作

1. 固有名詞が出たという理由だけで毎回検索しない。対象を知らない・確信がない、具体的な事実が必要、
   最新情報が必要、ユーザーが調査を求めた場合に依頼する。
2. 今回なら対象を確認した時点で短い背景調査を始める。検索中は、すでに分かっている会話内容に沿って続けられる。
3. 返却内容は簡潔な確認済み情報、取得時刻、出典URL。未取得の情報を知っているふりや調査済みのように話さない。
4. 検索結果は、その対象の話題が続いていれば自然に使う。話題が変わっていれば無理に読み上げない。
5. 同じ対象への短時間の重複検索を抑え、対象が曖昧なときは先に聞き返す。

検索結果をLiveへ渡す際は、背景知識としての `session.thinking.append` と、
今伝える結果の `session.commentary.append` を使い分けられる。
この会話制御と検索専用の応答形式・出典管理は、実装時に追加する範囲である。
